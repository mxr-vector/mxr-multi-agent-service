# 受控查询分解（multihop-query-decomposition）最终实验报告（2026-08-24）

## 实验设置

- 语料：LongBench 5 子集 t1 建库；两臂各 1000 条生产语义臂
  （`--multihop-only-multihop`），全部 1000/1000 成功（0 timeout / 0 failed，门槛达标）
- 对照臂：当前终态（双塔 qwen3-embeddings-4b + 席位 5 + 实体扩展），无分解
- 分解臂：`MULTIHOP_DECOMPOSE_ENABLED=true`，chat 角色 1 次调用（5s 超时、不重试、
  temp=0），≤3 条子查询并行召回入合并池，终排口径仍为原问题（无席位保护）

## 多跳子集对比

| 臂 | bridge@10 | hop@10 | recall@10 | 延迟 |
|---|---|---|---|---|
| 对照（终态无分解） | 0.137 | 0.474 | 0.188 | 5.5s |
| 分解臂 | 0.138 | 0.473 | 0.187 | 12.5s |

全类型加权：两臂完全持平（bridge@10 0.382 / recall@10 0.407 / 0.406）；
单跳与跨文档题型逐指标相同（分解只作用于多跳路径，隔离验证通过）。

| 通道启用 | 600/1000（仅多跳题） |
| 分解成功率 | 580/600 = 96.7% |
| 平均子查询数 | 2.63 |
| 分解调用平均耗时 | 1295ms |
| 失败归因 | parse_empty 13、timeout 7（全部静默降级，零阻断） |

## 贡献归因（诚实的负面结果）

分解臂跳组归因（1401 组）：最终命中 805（57.5%）/ 池内被裁 338（24.1%）/
召回未中 258（18.4%）。**经由分解候选命中的跳组：3/805（0.4%）**——
分解召回的文档几乎全部与既有通道重复或被终排淘汰。

对照臂召回未中桶（对比历史 44.3% → 当前口径 18.4%）未被分解进一步回收：
分解新增候选没有带来新的 gold。

## 结论

1. **机制全部达标**：成功率 96.7%、三重降级无阻断、成本 ≤1 次/多跳、题型零影响
2. **质量贡献为零**：多跳主指标 +0.001（噪声带内），未达验收判据（≥+0.01 且
   归因指向分解）；**开关保持默认关闭**，不进入生产默认路径
3. **认知更新**：召回未中桶的瓶颈不在"查询改写/理解"——子查询召回的文档与
   现有通道高度重复，说明候选池已覆盖可召回集合，剩余损失在**语料/块级对齐**
   层（gold 段落与叶块切分错位、桥接事实分散在未被检索命中的块内）。
   后续方向应从"查询侧"转向"索引侧"：路线 B 离线边增强（桥接事实句预验证入库）
   是更对症的下一站
