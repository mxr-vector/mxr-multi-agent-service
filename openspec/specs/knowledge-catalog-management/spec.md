# knowledge-catalog-management Specification

## Purpose

Provide the knowledge catalog capability: categories and knowledge bases backed
by an async PostgreSQL stack. Categories are managed as a flat structure the
client assembles into a tree; knowledge bases store metadata only (no vector
store side effects) and are soft-deleted. All endpoints return the unified
response envelope and convert expected failures into failure responses.

## Requirements

### Requirement: Async PostgreSQL access foundation
The system SHALL access PostgreSQL through an async SQLAlchemy stack (asyncpg driver) using a process-level cached async engine and session factory built from the existing async connection configuration, and business code SHALL obtain sessions from that factory rather than constructing engines directly.

#### Scenario: Reuse a single cached engine
- **WHEN** catalog operations run during the process lifetime
- **THEN** they use one cached async engine and session factory created from `PostgresConfig.async_connection`

#### Scenario: ORM ids generated by the database
- **WHEN** a category or knowledge base row is created without an explicit id
- **THEN** the id is generated by the database `uuidv7()` server-side default

### Requirement: Category creation and listing
The system SHALL create categories and return categories as a flat list so the client can assemble the tree, without server-side recursive tree construction. The listing SHALL return all categories by default and SHALL accept an optional `parent_id` filter that narrows the result to the direct children of that node.

#### Scenario: Create a category
- **WHEN** a category is created with a name (and optional `parent_id` and `sort_order`)
- **THEN** the system inserts the row and returns the created category including its generated id

#### Scenario: List categories flat
- **WHEN** categories are listed without a `parent_id` filter
- **THEN** the system returns a flat list of all category rows without nesting them into a tree

#### Scenario: List categories filtered by parent
- **WHEN** categories are listed with a `parent_id` filter
- **THEN** the system returns only the direct children of that parent as a flat list

### Requirement: Category retrieval by id
The system SHALL return a single category by id and SHALL report a not-found failure when the id does not exist.

#### Scenario: Get an existing category
- **WHEN** an existing category id is requested
- **THEN** the system returns that category

#### Scenario: Get a missing category
- **WHEN** a non-existent category id is requested
- **THEN** the system returns a not-found failure rather than an unhandled error

### Requirement: Category update
The system SHALL update a category's `name`, `sort_order`, and `parent_id`, and SHALL set `updated_at` explicitly on update.

#### Scenario: Update category fields
- **WHEN** a category update supplies new `name`, `sort_order`, or `parent_id` values
- **THEN** the system persists those values and updates `updated_at`

### Requirement: Guarded category hard deletion
The system SHALL physically delete a category only when it has no child categories and no knowledge base references it; otherwise the deletion SHALL be refused with a descriptive failure.

#### Scenario: Delete an empty category
- **WHEN** a category with no child categories and no referencing knowledge base is deleted
- **THEN** the system physically removes the row

#### Scenario: Refuse deletion of a non-empty category
- **WHEN** a category that has child categories or is referenced by at least one knowledge base is deleted
- **THEN** the system refuses the deletion and returns a descriptive "category not empty" failure without removing the row

### Requirement: Knowledge base creation with unique code and no Qdrant side effect
The system SHALL create a knowledge base storing metadata only, SHALL enforce the unique `code` constraint by returning a graceful failure on conflict, and SHALL NOT create a Qdrant collection during creation.

#### Scenario: Create a knowledge base
- **WHEN** a knowledge base is created with a unique `code` and required metadata
- **THEN** the system inserts the row, persists `qdrant_collection` as a stored name, and returns the created knowledge base

#### Scenario: Duplicate code is rejected gracefully
- **WHEN** a knowledge base is created with a `code` that already exists
- **THEN** the system returns a duplicate-code failure rather than surfacing an unhandled database error

#### Scenario: No vector store side effect on create
- **WHEN** a knowledge base is created
- **THEN** the system does not create or modify any Qdrant collection

### Requirement: Knowledge base listing and retrieval
The system SHALL list knowledge bases excluding soft-deleted rows and optionally filtered by `category_id`, and SHALL return a single knowledge base by id with a not-found failure when absent.

#### Scenario: List excludes soft-deleted
- **WHEN** knowledge bases are listed
- **THEN** rows with `status = 'deleted'` are excluded from the result

#### Scenario: List filtered by category
- **WHEN** knowledge bases are listed with a `category_id` filter
- **THEN** only knowledge bases referencing that category are returned

#### Scenario: Get a missing knowledge base
- **WHEN** a non-existent knowledge base id is requested
- **THEN** the system returns a not-found failure

### Requirement: Knowledge base metadata update
The system SHALL update only knowledge base metadata fields (`name`, `description`, `category_id`, `icon`, `visibility`, `owner`, `status`) and SHALL treat `code`, `qdrant_collection`, and the embedding fields as immutable after creation. Status transitions between `active` and `archived` SHALL be performed through this metadata update, not through dedicated archive/restore endpoints.

#### Scenario: Update editable metadata
- **WHEN** a knowledge base update supplies new values for editable metadata fields
- **THEN** the system persists those values and updates `updated_at`

#### Scenario: Transition status between active and archived
- **WHEN** a knowledge base update sets `status` to `archived` or back to `active`
- **THEN** the system persists the new status through the same metadata update path

#### Scenario: Immutable fields are not changed
- **WHEN** a knowledge base update attempts to change `code`, `qdrant_collection`, or an embedding field
- **THEN** the system does not modify those fields

### Requirement: Knowledge base soft deletion
The system SHALL soft-delete a knowledge base by setting its `status` to `deleted` rather than removing the row.

#### Scenario: Soft delete a knowledge base
- **WHEN** a knowledge base is deleted
- **THEN** the system sets `status = 'deleted'`, keeps the row, and the knowledge base no longer appears in listings

### Requirement: Unified response and error handling
The system SHALL return every catalog endpoint result through the unified response envelope, converting expected failures (duplicate code, not found, guarded-delete conflict) into failure responses rather than unhandled server errors.

#### Scenario: Successful operation envelope
- **WHEN** a catalog operation succeeds
- **THEN** the system returns a success envelope carrying the result data

#### Scenario: Expected failure envelope
- **WHEN** an operation fails for a duplicate code, a missing entity, or a guarded-delete conflict
- **THEN** the system returns a failure envelope with a clear message instead of an HTTP 500
