# knowledge-catalog-management Specification

## Purpose

Provide the knowledge catalog capability: knowledge bases and their internal
folders backed by an async PostgreSQL stack. Folders belong to exactly one
knowledge base and are managed as a flat structure the client assembles into a
tree; knowledge bases store metadata only (no vector store side effects) and
are soft-deleted. All endpoints return the unified response envelope and
convert expected failures into failure responses.

## Requirements

### Requirement: Async PostgreSQL access foundation
The system SHALL access PostgreSQL through an async SQLAlchemy stack (asyncpg driver) using a process-level cached async engine and session factory built from the existing async connection configuration, and business code SHALL obtain sessions from that factory rather than constructing engines directly.

#### Scenario: Reuse a single cached engine
- **WHEN** catalog operations run during the process lifetime
- **THEN** they use one cached async engine and session factory created from `PostgresConfig.async_connection`

#### Scenario: ORM ids generated by the database
- **WHEN** a folder or knowledge base row is created without an explicit id
- **THEN** the id is generated by the database `uuidv7()` server-side default

### Requirement: Folder creation and listing scoped to a knowledge base
The system SHALL create folders that belong to exactly one knowledge base
(`knowledge_base_id` required and immutable) and SHALL return folders as a
flat list scoped to one knowledge base so the client can assemble the tree,
without server-side recursive tree construction. Folder creation SHALL fail
with a business error when the knowledge base does not exist (or is deleted),
or when the supplied `parent_id` refers to a folder of a different knowledge
base. The listing SHALL require a `knowledge_base_id` filter and SHALL accept
an optional `parent_id` filter narrowing the result to direct children.

#### Scenario: Create a folder inside a knowledge base
- **WHEN** a folder is created with a name and a valid `knowledge_base_id`
  (and optional same-KB `parent_id` and `sort_order`)
- **THEN** the system inserts the row and returns the created folder including
  its generated id and `knowledge_base_id`

#### Scenario: Reject a cross-knowledge-base parent
- **WHEN** a folder is created or re-parented with a `parent_id` belonging to
  a different knowledge base
- **THEN** the system returns a business failure and does not persist the change

#### Scenario: List folders of one knowledge base flat
- **WHEN** folders are listed with a `knowledge_base_id`
- **THEN** the system returns a flat list of that knowledge base's folder rows
  without nesting them into a tree

#### Scenario: List folders filtered by parent
- **WHEN** folders are listed with `knowledge_base_id` and a `parent_id` filter
- **THEN** the system returns only the direct children of that parent as a
  flat list

### Requirement: Folder retrieval by id
The system SHALL return a single folder by id and SHALL report a not-found
failure when the id does not exist.

#### Scenario: Get an existing folder
- **WHEN** an existing folder id is requested
- **THEN** the system returns that folder

#### Scenario: Get a missing folder
- **WHEN** a non-existent folder id is requested
- **THEN** the system returns a not-found failure rather than an unhandled error

### Requirement: Folder update
The system SHALL update a folder's `name`, `sort_order`, and `parent_id`, SHALL
treat `knowledge_base_id` as immutable after creation, and SHALL set
`updated_at` explicitly on update.

#### Scenario: Update folder fields
- **WHEN** a folder update supplies new `name`, `sort_order`, or `parent_id`
  values (with `parent_id` in the same knowledge base)
- **THEN** the system persists those values and updates `updated_at`

#### Scenario: Knowledge base binding is immutable
- **WHEN** a folder update attempts to change `knowledge_base_id`
- **THEN** the system does not modify that field

### Requirement: Guarded folder hard deletion
The system SHALL physically delete a folder only when it has no child folders
and no non-deleted document references it; otherwise the deletion SHALL be
refused with a descriptive failure.

#### Scenario: Delete an empty folder
- **WHEN** a folder with no child folders and no referencing document is deleted
- **THEN** the system physically removes the row

#### Scenario: Refuse deletion of a non-empty folder
- **WHEN** a folder that has child folders or is referenced by at least one
  non-deleted document is deleted
- **THEN** the system refuses the deletion and returns a descriptive "folder
  not empty" failure without removing the row

### Requirement: Knowledge base creation with unique code and no Qdrant side effect
The system SHALL create a knowledge base storing metadata only, SHALL enforce the unique `code` constraint by returning a graceful failure on conflict, and SHALL NOT create a Qdrant collection during creation.

#### Scenario: Create a knowledge base
- **WHEN** a knowledge base is created with a unique `code` and required metadata
- **THEN** the system inserts the row, persists `qdrant_collection` as a stored name, and returns the created knowledge base

#### Scenario: Duplicate code is rejected gracefully
- **WHEN** a knowledge base is created with a `code` that already exists
- **THEN** the system returns a duplicate-code failure rather than surfacing an unhandled database error

#### Scenario: No vector store side effect on create
- **WHEN** a knowledge base is created
- **THEN** the system does not create or modify any Qdrant collection

### Requirement: Knowledge base listing and retrieval
The system SHALL list knowledge bases excluding soft-deleted rows, optionally
filtered by a name/description keyword, and SHALL return a single knowledge
base by id with a not-found failure when absent. Knowledge bases SHALL NOT
carry or filter by any category/folder reference.

#### Scenario: List excludes soft-deleted
- **WHEN** knowledge bases are listed
- **THEN** rows with `status = 'deleted'` are excluded from the result

#### Scenario: No category dimension on knowledge bases
- **WHEN** a knowledge base is created, listed, or returned
- **THEN** its payload contains no `category_id`/folder field and the listing
  accepts no category/folder filter

#### Scenario: Get a missing knowledge base
- **WHEN** a non-existent knowledge base id is requested
- **THEN** the system returns a not-found failure

### Requirement: Knowledge base metadata update
The system SHALL update only knowledge base metadata fields (`name`,
`description`, `icon`, `visibility`, `owner`, `status`) and SHALL treat `code`,
`qdrant_collection`, and the embedding fields as immutable after creation.
Status transitions between `active` and `archived` SHALL be performed through
this metadata update, not through dedicated archive/restore endpoints.

#### Scenario: Update editable metadata
- **WHEN** a knowledge base update supplies new values for editable metadata fields
- **THEN** the system persists those values and updates `updated_at`

#### Scenario: Transition status between active and archived
- **WHEN** a knowledge base update sets `status` to `archived` or back to `active`
- **THEN** the system persists the new status through the same metadata update path

#### Scenario: Immutable fields are not changed
- **WHEN** a knowledge base update attempts to change `code`, `qdrant_collection`, or an embedding field
- **THEN** the system does not modify those fields

### Requirement: Knowledge base soft deletion
The system SHALL soft-delete a knowledge base by setting its `status` to `deleted` rather than removing the row.

#### Scenario: Soft delete a knowledge base
- **WHEN** a knowledge base is deleted
- **THEN** the system sets `status = 'deleted'`, keeps the row, and the knowledge base no longer appears in listings

### Requirement: Unified response and error handling
The system SHALL return every catalog endpoint result through the unified response envelope, converting expected failures (duplicate code, not found, guarded-delete conflict) into failure responses rather than unhandled server errors.

#### Scenario: Successful operation envelope
- **WHEN** a catalog operation succeeds
- **THEN** the system returns a success envelope carrying the result data

#### Scenario: Expected failure envelope
- **WHEN** an operation fails for a duplicate code, a missing entity, or a guarded-delete conflict
- **THEN** the system returns a failure envelope with a clear message instead of an HTTP 500
