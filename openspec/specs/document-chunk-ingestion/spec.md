# document-chunk-ingestion Specification

## Purpose

Provide the document ingestion capability for knowledge bases: uploaded files are
parsed by type, split into a two-level parent/child chunk tree, and persisted to
PostgreSQL with no vector-store side effects. Vectorization is a separate,
explicit trigger keyed by chunk id into the owning knowledge base's Qdrant
collection. Re-uploads are deduplicated by `content_hash` with versioning, and
knowledge base counts stay in sync. All endpoints return the unified response
envelope and convert expected failures into failure responses.

## Requirements

### Requirement: Document ORM models with server-side ids and no relationships
The system SHALL map `rag_documents` and `rag_chunks` as SQLAlchemy ORM models bound to the shared declarative `Base`, with ids generated by the database `uuidv7()` server-side default and no foreign keys or ORM relationships, delegating referential integrity to the business layer.

#### Scenario: Ids generated by the database
- **WHEN** a document or chunk row is inserted without an explicit id
- **THEN** the id is generated by the database `uuidv7()` server-side default

#### Scenario: Associations are plain columns
- **WHEN** a chunk references its document or parent chunk
- **THEN** `document_id` and `parent_chunk_id` are stored as plain UUID columns with no foreign-key constraint

### Requirement: File upload parsing and persistence without vectorization
The system SHALL accept an uploaded file for a knowledge base, parse it by type (pdf, markdown, excel, docx), split it into a two-level parent/child chunk tree, and persist the document and all chunks to PostgreSQL, without embedding or writing to Qdrant. The system SHALL reject an unsupported file type and an unknown knowledge base with a failure response.

#### Scenario: Upload a supported file
- **WHEN** a supported file (pdf/markdown/excel/docx) is uploaded referencing an existing knowledge base
- **THEN** the system parses it, inserts one `rag_documents` row (`version = 1`, not-yet-indexed status) and its parent/child chunk rows, and writes nothing to Qdrant

#### Scenario: Upload for an unknown knowledge base
- **WHEN** a file is uploaded referencing a knowledge base id that does not exist
- **THEN** the system returns a not-found failure and persists nothing

#### Scenario: Unsupported file type
- **WHEN** a file whose type is not pdf/markdown/excel/docx is uploaded
- **THEN** the system returns an unsupported-file-type failure and persists nothing

### Requirement: Two-level parent-child chunking
The system SHALL split a document into level 1 parent chunks and level 0 leaf chunks, set each leaf chunk's `parent_chunk_id` to its parent chunk, assign `chunk_index` sequentially within each `(document_id, document_version, level)`, and stamp every chunk with the document's current `document_version`.

#### Scenario: Leaf chunks reference their parent
- **WHEN** a document is split
- **THEN** each level 0 chunk has a `parent_chunk_id` pointing at a level 1 chunk of the same document and version

#### Scenario: Only level 0 is destined for the vector store
- **WHEN** a document is split
- **THEN** level 1 parent chunks are persisted in PostgreSQL only and are not embedded or upserted to Qdrant

### Requirement: Separate vectorization trigger keyed by chunk id
The system SHALL vectorize a document only on an explicit trigger, embedding the current version's level 0 chunks and upserting them into the owning knowledge base's `qdrant_collection` using each `rag_chunks.id` as the Qdrant point id, with payload carrying document/knowledge-base identifiers and chapter/page/validity fields plus the chunk text. Triggering vectorization on an absent or chunk-less document SHALL return a failure.

#### Scenario: Vectorize an uploaded document
- **WHEN** vectorization is triggered for a document that has level 0 chunks
- **THEN** the system embeds those chunks and upserts them into the knowledge base's `qdrant_collection` with the Qdrant point id equal to each chunk's id, and marks the document indexed

#### Scenario: Vectorize keeps the collection per knowledge base
- **WHEN** vectorization runs
- **THEN** points are written to the knowledge base's configured `qdrant_collection`, not a global hardcoded collection

#### Scenario: Vectorize an absent or empty document
- **WHEN** vectorization is triggered for a non-existent document or one with no level 0 chunks
- **THEN** the system returns a failure rather than an unhandled error

### Requirement: content_hash skip-if-unchanged on re-upload
The system SHALL compute a `content_hash` over the parsed document text and, on re-upload of the same knowledge base and `source_uri`, skip re-splitting and re-vectorizing when the hash is unchanged, and otherwise create a new `document_version` chunk set for the changed content.

#### Scenario: Unchanged re-upload is a no-op
- **WHEN** a file with the same `source_uri` and identical `content_hash` is re-uploaded to the same knowledge base
- **THEN** the system returns the existing document without creating new chunks or re-vectorizing

#### Scenario: Changed re-upload creates a new version
- **WHEN** a file with the same `source_uri` but a different `content_hash` is re-uploaded
- **THEN** the system increments the document `version`, replaces its content and `content_hash`, and writes a fresh chunk set stamped with the new `document_version`

#### Scenario: Stale version is removed after re-vectorization
- **WHEN** a re-versioned document is vectorized
- **THEN** the new version's points are written before the previous version's chunks and Qdrant points are removed

### Requirement: Metadata-only document update
The system SHALL update only a document's descriptive and validity metadata and set `updated_at` explicitly, and SHALL NOT change content, `content_hash`, `version`, knowledge base ownership, indexing status, or trigger any re-split or re-vectorization.

#### Scenario: Update editable metadata
- **WHEN** a document update supplies new descriptive/validity fields (such as `title`, `metadata`, or `valid_until`)
- **THEN** the system persists those values and updates `updated_at`

#### Scenario: Content-bearing fields are untouched
- **WHEN** a document metadata update is applied
- **THEN** the system leaves `content`, `content_hash`, `version`, and `knowledge_base_id` unchanged and does not re-split or re-vectorize

### Requirement: Folder assignment consistency with the knowledge base
When a document is created or updated with a `folder_id`, the system SHALL
verify that the folder exists and belongs to the same knowledge base as the
document, rejecting the operation with a business failure otherwise. A missing
`folder_id` SHALL remain valid (document lives at the knowledge base root).

#### Scenario: Upload into a folder of the same knowledge base
- **WHEN** a document is uploaded with a `folder_id` whose folder belongs to
  the target knowledge base
- **THEN** the document is persisted with that `folder_id`

#### Scenario: Reject a folder from another knowledge base
- **WHEN** a document is uploaded or updated with a `folder_id` whose folder
  belongs to a different knowledge base (or does not exist)
- **THEN** the system returns a business failure and does not persist the
  assignment

#### Scenario: Upload without a folder
- **WHEN** a document is uploaded without a `folder_id`
- **THEN** the document is persisted at the knowledge base root
  (`folder_id` NULL)

### Requirement: Document browsing
The system SHALL list documents for a knowledge base excluding soft-deleted rows, with pagination, and SHALL return a single document by id with a not-found failure when absent.

#### Scenario: List documents by knowledge base
- **WHEN** documents are listed for a knowledge base id with pagination
- **THEN** the system returns that knowledge base's documents excluding `status = 'deleted'`

#### Scenario: Get a missing document
- **WHEN** a non-existent document id is requested
- **THEN** the system returns a not-found failure

### Requirement: Chunk browsing (read-only)
The system SHALL list chunks for a document ordered by `chunk_index`, with optional `level` and `document_version` filters and pagination, and SHALL return a single chunk by id with a not-found failure when absent. The system SHALL NOT expose chunk create, update, or delete operations.

#### Scenario: List chunks by document
- **WHEN** chunks are listed for a document id
- **THEN** the system returns that document's chunks ordered by `chunk_index`

#### Scenario: Filter chunks by level
- **WHEN** chunks are listed with a `level` filter
- **THEN** the system returns only chunks at that level (for example, level 0 leaves or level 1 parents)

#### Scenario: Get a missing chunk
- **WHEN** a non-existent chunk id is requested
- **THEN** the system returns a not-found failure

### Requirement: Knowledge base count synchronization
The system SHALL keep the owning knowledge base's `document_count` and `total_chunk_count` in sync within the same transaction as the document/chunk write, counting only currently-effective (latest version) rows.

#### Scenario: Counts increase on new document
- **WHEN** a new document and its chunks are persisted
- **THEN** the knowledge base's `document_count` and `total_chunk_count` are increased accordingly in the same transaction

#### Scenario: Counts unchanged on no-op re-upload
- **WHEN** an unchanged file is re-uploaded and skipped
- **THEN** the knowledge base's counts are not changed

#### Scenario: Chunk count reflects the effective version
- **WHEN** a document is re-versioned and the old version's chunks are removed
- **THEN** `total_chunk_count` reflects the latest version's leaf-chunk count, not the sum of all versions

### Requirement: Unified response and error handling
The system SHALL return every document and chunk endpoint result through the unified response envelope, converting expected failures (unknown knowledge base, unknown document/chunk, unsupported file type, vectorize on an empty/absent document) into failure responses rather than unhandled server errors.

#### Scenario: Successful operation envelope
- **WHEN** a document or chunk operation succeeds
- **THEN** the system returns a success envelope carrying the result data

#### Scenario: Expected failure envelope
- **WHEN** an operation fails for an unknown knowledge base, an unknown document/chunk, an unsupported file type, or vectorization of an empty/absent document
- **THEN** the system returns a failure envelope with a clear message instead of an HTTP 500
